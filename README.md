# imigrate-platform

Terraform for **imigrate.com**, the wedding-management platform. One isolated
DigitalOcean stack per wedding: its own Managed Postgres cluster, its own Spaces
bucket and CDN for guest media, its own App Platform app, its own DigitalOcean
project, and one subdomain under `imigrate.com`.

The application itself is not in this repo. It lives at
[`imigrate-apps/wedding-app`](https://github.com/imigrate-apps/wedding-app) —
Next.js 15, App Router, `output: "standalone"`. This repo provisions the
infrastructure it runs on and injects its configuration.

## What a wedding stack contains

| Resource | Module | Notes |
| --- | --- | --- |
| Managed Postgres 16 cluster, database, role | `wedding-data` | Single node by default. Password generated by DigitalOcean. |
| Postgres trusted-sources firewall | `wedding-data` | `type = "app"` rule scoped to this wedding's app only. |
| Spaces bucket for guest media | `wedding-data` | Private bucket, public-read objects. Versioned, with lifecycle rules. |
| Spaces CDN endpoint + CORS | `wedding-data` | Long edge TTL; guest media is immutable. |
| App Platform app (one `service`) | `wedding-app` | Next.js standalone, `http_port = 3000`, health check, alerts. |
| `DEPLOYMENT_FAILED` / `DOMAIN_FAILED` alerts | `wedding-app` | The two failures that present as "the site is down". |
| CNAME under `imigrate.com` | `wedding-dns` | Points at the app's permanent `*.ondigitalocean.app` ingress. |
| DigitalOcean project | env root | One per wedding, so billing breaks down per wedding. |

Weddings share exactly two things, both created once in `envs/_shared`: the
`imigrate.com` DNS **zone** and a regional **VPC**. Nothing else — no shared
database, no shared bucket, no shared credentials.

## Repository layout

```
imigrate-platform/
├── README.md
├── .gitignore
├── versions.tf          ┐
├── providers.tf         │  Root scaffold. NOT applied directly -- this is the
├── variables.tf         │  template a new envs/<slug>/ is built from, kept as
├── backend.tf           ┘  a valid module so fmt/validate cover it in CI.
├── modules/
│   ├── wedding-data/    Postgres + Spaces + CDN + firewall
│   ├── wedding-app/     App Platform app spec, domains, env, alerts
│   └── wedding-dns/     records under the apex zone
├── envs/
│   ├── _shared/         apex DNS zone, shared VPC, platform project  (apply FIRST)
│   ├── staging/         the platform's own rehearsal stack
│   └── muskan-sourav/   one real wedding
└── .github/workflows/
    ├── terraform-plan.yml   plan on PR, sticky plan comment
    └── terraform-apply.yml  gated apply on merge to main
```

**The real root modules are the directories under `envs/`.** Each one is
self-contained: it declares its own `terraform` and `provider` blocks, its own
variables, and its own backend key. The files at the repo root are the scaffold
those are copied from — there is no `main.tf` at the root and nothing is created
by applying it.

Why duplicate the `terraform` / `provider` block into every env instead of
sharing one file? Because plain Terraform has no include mechanism, and the
alternatives (symlinks, a code generator, Terragrunt) each cost more than the
fifteen lines they save. The duplication is small, static, and `terraform fmt
-recursive` and `terraform validate` in CI keep it honest.

| DigitalOcean account with billing enabled | Managed Postgres and App Platform are paid from the first minute. |

## Remote state bootstrap

State lives in a DigitalOcean Spaces bucket, using Terraform's `s3` backend.
This creates a chicken-and-egg problem: **Terraform cannot create the bucket
that holds its own state**, because the very first `terraform init` needs that
bucket to already exist.

So the state bucket is created **once, by hand, outside Terraform**, and is
deliberately never adopted into any configuration. It is the one piece of
infrastructure here that is not code, and that is correct: a bootstrap resource
that manages its own manager is a trap, not a feature.

### One-time setup

```bash
# 1. Credentials. The Spaces key doubles as the S3 credential for the backend.
export DIGITALOCEAN_TOKEN='...'
export SPACES_ACCESS_KEY_ID='...'
export SPACES_SECRET_ACCESS_KEY='...'
export AWS_ACCESS_KEY_ID="$SPACES_ACCESS_KEY_ID"
export AWS_SECRET_ACCESS_KEY="$SPACES_SECRET_ACCESS_KEY"

# 2. Create the bucket. Pick a globally unique name -- Spaces bucket names are
#    shared across every DigitalOcean customer.
doctl spaces bucket create imigrate-tfstate --region sgp1

#    ...or with the AWS CLI, which also works against Spaces:
aws s3api create-bucket \
  --bucket imigrate-tfstate \
  --endpoint-url https://sgp1.digitaloceanspaces.com

# 3. Turn on versioning. This is the actual recovery mechanism for a
#    corrupted or truncated state file -- do not skip it.
aws s3api put-bucket-versioning \
  --bucket imigrate-tfstate \
  --versioning-configuration Status=Enabled \
  --endpoint-url https://sgp1.digitaloceanspaces.com

# 4. Confirm the bucket is NOT public.
aws s3api get-bucket-acl \
  --bucket imigrate-tfstate \
  --endpoint-url https://sgp1.digitaloceanspaces.com
```

The state file contains the Postgres password, the JWT signing secret and the
MSG91 key in cleartext. Treat this bucket as production credentials.

### Why every `skip_*` flag is set

Spaces speaks S3 but is not AWS, so the backend's AWS-specific preflight checks
all have to be disabled:

| Flag | Reason |
| --- | --- |
| `skip_credentials_validation` | There is no STS endpoint to validate against. |
| `skip_requesting_account_id` | There is no IAM/STS account to look up. |
| `skip_metadata_api_check` | There is no EC2 instance metadata service. |
| `skip_region_validation` | `blr1` is not an AWS region name. |
| `skip_s3_checksum` | Spaces rejects the trailing checksum headers newer AWS SDKs add by default. Without this, writes fail with an opaque `400`. |

`region = "us-east-1"` in the backend block is a dummy value the SDK insists
on; the real placement comes from the `endpoints.s3` hostname.

### No state locking — read this

DigitalOcean Spaces does not reliably support the S3 conditional-write
primitive that Terraform's `use_lockfile` locking depends on, and there is no
DynamoDB equivalent. **This repo runs without backend locking.**

What stands in for it:

- every apply runs through `terraform-apply.yml`, which has a per-stack
  `concurrency` group, so two applies of the same stack cannot overlap;
- state bucket versioning, so a clobbered state file can be rolled back;
- and the rule that **nobody applies from a laptop** while CI may be applying.

If you verify that conditional writes work on your Spaces region, add
`use_lockfile = true` to each `backend.tf` and this caveat goes away.

## Applying a stack

`envs/_shared` **must be applied first** — it creates the DNS zone every
wedding stack reads and the VPC they share.

```bash
# ---- shared, once ---------------------------------------------------------
cd envs/_shared

terraform init \
  -backend-config="bucket=imigrate-tfstate" \
  -backend-config="key=shared/terraform.tfstate"

terraform plan  -out=tfplan
terraform apply tfplan

# Note the VPC id -- every wedding stack takes it as an input.
terraform output -raw vpc_uuid
```

```bash
# ---- one wedding ----------------------------------------------------------
cd ../muskan-sourav

cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars          # replace every REPLACE_ME, set vpc_uuid

terraform init \
  -backend-config="bucket=imigrate-tfstate" \
  -backend-config="key=weddings/muskan-sourav/terraform.tfstate"

terraform fmt -check -recursive ../..
terraform validate
terraform plan -out=tfplan

# Read the plan. Then:
terraform apply tfplan
```

`terraform.tfvars` is git-ignored. For CI, or if you would rather not have
secrets on disk at all, export them instead:

```bash
export TF_VAR_jwt_secret="$(openssl rand -base64 48)"
export TF_VAR_msg91_auth_key='...'
export TF_VAR_app_spaces_access_key_id='...'
export TF_VAR_app_spaces_secret_access_key='...'
```

### What to expect on the first apply

1. The Postgres cluster takes **5–10 minutes** to provision. Nothing is wrong.
2. The App Platform build takes another **5–10 minutes** on the Basic tier.
3. The Postgres firewall rule shows as `(known after apply)` in the first plan,
   because it depends on an app id that does not exist yet. This is expected.
4. The wedding's certificate is issued only **after** the CNAME resolves, so
   `terraform output app_url` may still show the `*.ondigitalocean.app`
   hostname for a few minutes. DigitalOcean retries on its own.

## Adding a new wedding

```bash
SLUG=priya-arjun

cp -r envs/muskan-sourav "envs/${SLUG}"
cd "envs/${SLUG}"

# 1. Point the tfvars at the new wedding.
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars      # wedding_slug = "priya-arjun", new secrets,
                              # vpc_uuid from envs/_shared

# 2. Change the default in main.tf so a missing tfvars cannot silently
#    apply someone else's wedding.
$EDITOR main.tf               # variable "wedding_slug" { default = "priya-arjun" }

# 3. Make sure no state was copied along.
rm -rf .terraform .terraform.lock.hcl terraform.tfstate*

# 4. Initialise against a FRESH state key. Getting this wrong points the new
#    wedding at an existing wedding's state, and the first apply would try to
#    rename that wedding's live infrastructure.
terraform init \
  -backend-config="bucket=imigrate-tfstate" \
  -backend-config="key=weddings/${SLUG}/terraform.tfstate"

terraform plan -out=tfplan     # expect ~10 resources to CREATE, 0 to change
```

Then, before merging:

1. Create a **GitHub Environment** named exactly `priya-arjun`
   (Settings → Environments). Add required reviewers to it — the environment is
   what gates apply, and without reviewers it is only a label.
2. Add that environment's secrets: `DIGITALOCEAN_ACCESS_TOKEN`,
   `SPACES_ACCESS_KEY_ID`, `SPACES_SECRET_ACCESS_KEY`, `JWT_SECRET`,
   `MSG91_AUTH_KEY`, `APP_SPACES_ACCESS_KEY_ID`,
   `APP_SPACES_SECRET_ACCESS_KEY`; and variables `MSG91_TEMPLATE_ID`,
   `ADMIN_PHONES`, `SHARED_VPC_UUID`.
3. Open a PR. `terraform-plan.yml` discovers `envs/priya-arjun/` automatically
   and comments the plan.

**Every wedding gets a fresh `jwt_secret`.** Reusing one across weddings means a
session token minted for one couple's site is valid on another's.

## Attaching a customer's custom domain

A couple who buys `muskanandsourav.in` keeps it at their own registrar.
DigitalOcean cannot manage DNS it does not host, so the split is:

- **Terraform** registers the domain with App Platform, which provisions and
  renews the TLS certificate.
- **The customer** creates one DNS record at their registrar.

### 1. Register the domain with the app

In `envs/<slug>/terraform.tfvars`:

```hcl
custom_domains = [
  { name = "muskanandsourav.in",     type = "ALIAS" },
  { name = "www.muskanandsourav.in", type = "ALIAS" },
]
```

`terraform apply`. The app now lists the domain as pending verification.

### 2. Give the customer the CNAME target

```bash
terraform output -raw app_default_ingress
# https://muskan-sourav-production-ab12c.ondigitalocean.app
```

They create, at their registrar:

| Host | Type | Value |
| --- | --- | --- |
| `www` | CNAME | `muskan-sourav-production-ab12c.ondigitalocean.app.` |
| `@` | ALIAS / ANAME / CNAME-flattening | same value |

The apex (`@`) needs a provider that supports ALIAS, ANAME or CNAME flattening
— Cloudflare, Route 53 and most Indian registrars' "web forwarding" do not all
behave the same. If theirs cannot do it, the usual answer is to serve the site
at `www.` and redirect the apex.

**Always give them `app_default_ingress`, never `app_url`.** Once the custom
domain's certificate issues, `app_url` *becomes* that custom domain, and a
CNAME pointing at itself is a resolution loop.

### 3. Wait for the certificate

DigitalOcean issues a Let's Encrypt certificate once the record resolves —
usually minutes, occasionally an hour if the registrar's TTL is long. The
`DOMAIN_FAILED` alert fires if it does not.

### 4. Optionally make it primary

Change that domain's `type` to `"PRIMARY"` and set `site_url` accordingly, so
`NEXT_PUBLIC_SITE_URL` and the links in invitation messages use the couple's own
domain. This triggers a rebuild, because `NEXT_PUBLIC_*` is baked in at build
time.

## Design decisions

### The apex domain is created once, not per wedding

`digitalocean_domain` is a DNS **zone**, and a zone is a singleton per account.
If each wedding stack declared it, the second `apply` would fail with *domain
already exists* — and if you imported it into each stack instead, destroying
**one** finished wedding would delete the zone and take every other wedding
offline.

So `envs/_shared` creates it, and `modules/wedding-dns` reads it:

```hcl
data "digitalocean_domain" "apex" {
  name = var.apex_domain
}
```

Individual `digitalocean_record` resources *are* owned per wedding — a record is
scoped to one name, so destroying a wedding removes only its own records.

### Bucket private, objects public

The bucket ACL is `private`; the application sets `public-read` on each object
as it uploads. A public bucket would also expose `ListObjects`, letting anyone
enumerate every photo of every guest. The tradeoff is that a public-read object
is readable by anyone holding its URL — unguessable keys are obscurity, not
permission. For genuinely private media, serve pre-signed GET URLs from the app;
the bucket ACL does not need to change.

### App Platform never manages DNS (`zone` is never set)

`digitalocean_app`'s `domain` block can take a `zone`, which makes App Platform
create the DNS record itself. We never set it, so that DNS has exactly one
owner — Terraform, via `wedding-dns` — and so that the runbook for an
imigrate.com subdomain and a customer's own domain is identical: point a CNAME
at `default_ingress`, wait for the certificate.

### Tagging and labelling

Only `digitalocean_database_cluster` accepts `tags` — App Platform apps, Spaces
buckets, CDN endpoints, domains and records have no tag argument in the
DigitalOcean API. So the wedding slug and environment are carried four ways:

1. **DO tags** on the Postgres cluster: `imigrate`, `wedding:<slug>`,
   `env:<environment>`, `component:data`.
2. **Resource names**: `<slug>-<environment>-pg`, `<slug>-media-<environment>`,
   `<slug>-<environment>` (app).
3. **DigitalOcean project**: `wedding-<slug>-<environment>`, which is what
   billing groups by.
4. **Runtime env vars**: `WEDDING_SLUG` and `APP_ENV` inside the app.

### Module wiring is not circular

`module.data`'s firewall depends on `module.app`; `module.app` depends on
`module.data`'s cluster. Terraform flattens modules and builds the graph per
*resource*, so the real order is:

```
database_cluster → database_db / database_user → app → database_firewall
```

## Secrets

**Nothing secret is committed.** `.gitignore` excludes `*.tfvars` (keeping only
`*.tfvars.example`), `*.tfplan`, `*.tfstate*` and `.env*`. Every value in the
example tfvars is an obvious `REPLACE_ME` placeholder.

Where secrets actually live:

| Secret | Source of truth | Reaches the app as |
| --- | --- | --- |
| DO API token | GitHub Environment secret / operator's shell | never |
| Spaces keys (Terraform) | GitHub Environment secret | never |
| Spaces keys (app) | GitHub Environment secret | `SPACES_KEY` / `SPACES_SECRET`, type `SECRET` |
| Postgres password | Generated by DigitalOcean | inside `DATABASE_URL`, type `SECRET` |
| `JWT_SECRET` | GitHub Environment secret | type `SECRET` |
| `MSG91_AUTH_KEY` | GitHub Environment secret | type `SECRET` |

### State is as sensitive as the secrets in it

`sensitive = true` masks console output. It does **not** encrypt state. The
Postgres password, the JWT secret and the MSG91 key are all in the state file in
cleartext. Anyone with read access to the state bucket has production. Keep it
private, keep versioning on, and give it its own Spaces key if you can.

Saved plan files (`tfplan`) have the same problem, which is why they are
git-ignored, never uploaded from a `pull_request` run, kept for one day when
they are uploaded, and deleted from the runner after apply.

### Rotation

```bash
# Postgres password
terraform taint 'module.data.digitalocean_database_user.app'
terraform apply    # new password, app redeployed with the new DATABASE_URL

# JWT secret -- invalidates every open guest session
export TF_VAR_jwt_secret="$(openssl rand -base64 48)"
terraform apply
```

## CI/CD

### `terraform-plan.yml` — on pull request

1. `terraform fmt -check -recursive` across the whole repo, once.
2. Works out which stacks the PR touches. A change under `modules/` or to a
   root `*.tf` plans **every** stack.
3. Per stack: `init` against that stack's state key → `validate` → `plan`.
4. Posts the plan as a **sticky** PR comment, one per stack, updated in place
   rather than appended. Output over 60 000 characters is tail-truncated,
   because GitHub rejects comments above 65 536.

This workflow never applies, and never uploads a plan artifact — a plan taken
from a pull request contains resolved secrets.

### `terraform-apply.yml` — on merge to main

```
discover → plan (artifact) → apply (Environment-gated, applies that artifact)
```

The apply job **does not re-plan**. It applies the exact plan file produced from
the same commit, so what the reviewer approved is what runs. If the world moved
since, Terraform rejects the stale plan instead of quietly doing something else.

Gating and safety:

- `environment: ${{ matrix.stack }}` — a GitHub Environment named for the
  wedding. **Add required reviewers to it**; without them the environment is
  only a label and there is no gate.
- `concurrency: terraform-apply-<stack>` with `cancel-in-progress: false` —
  this is what replaces backend state locking. Do not remove it.
- Secrets are scoped to the environment, so a job for one wedding cannot read
  another wedding's credentials.
- The plan artifact is `retention-days: 1` and the file is deleted from the
  runner in an `if: always()` step.

`workflow_dispatch` takes a single `stack` input, for applying one stack by
hand without pushing a commit.

### About OIDC

The workflows request `id-token: write` so an OIDC-federated backend can be
adopted later without editing permissions. **DigitalOcean's API does not
support OIDC federation today** — there is no way to exchange a GitHub OIDC
token for DO credentials. So authentication is a long-lived
`DIGITALOCEAN_ACCESS_TOKEN`, stored as a GitHub Environment secret and
protected by that environment's reviewers. Rotate it on a schedule.

### Required per-environment configuration

| Kind | Name |
| --- | --- |
| Secret | `DIGITALOCEAN_ACCESS_TOKEN` |
| Secret | `SPACES_ACCESS_KEY_ID`, `SPACES_SECRET_ACCESS_KEY` |
| Secret | `APP_SPACES_ACCESS_KEY_ID`, `APP_SPACES_SECRET_ACCESS_KEY` |
| Secret | `JWT_SECRET` |
| Secret | `MSG91_AUTH_KEY` |
| Variable | `MSG91_TEMPLATE_ID`, `ADMIN_PHONES`, `SHARED_VPC_UUID` |

## Decommissioning a wedding

A finished wedding costs the same as a live one. But guest photos are the one
thing a couple cannot get back, so destroy is deliberately manual and has no CI
path.

```bash
cd envs/<slug>

# 1. EXPORT THE MEDIA FIRST. This is irreversible.
aws s3 sync "s3://$(terraform output -raw bucket_name)" ./wedding-media-backup \
  --endpoint-url "https://$(terraform output -raw cdn_endpoint | cut -d. -f2).digitaloceanspaces.com"

# 2. Take a final database dump.
pg_dump "$(terraform output -raw database_uri)" -Fc -f wedding.dump

# 3. Read the full destroy plan. Every resource. No -target.
terraform plan -destroy -out=destroy.tfplan
terraform show -no-color destroy.tfplan | less

# 4. Only once someone has actually read that list:
terraform apply destroy.tfplan
```

The bucket will refuse to delete while it still holds objects unless
`bucket_force_destroy = true`. That refusal is a feature — leave the variable
alone until step 1 is genuinely done.

Never `terraform destroy` `envs/_shared`. It owns the `imigrate.com` zone;
destroying it takes every wedding offline at once.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `Error: domain already exists` on a wedding apply | A wedding stack is trying to create the apex zone | Only `envs/_shared` may create it. `wedding-dns` reads it as a data source. |
| Site loads but every image, font and stylesheet 404s | `public/` and `.next/static/` were not copied into `.next/standalone/` | Use the module's default `build_command`. |
| Every deploy fails its health check | Standalone server bound to `localhost` | `run_command` must set `HOSTNAME=0.0.0.0`. |
| `NEXT_PUBLIC_*` is `undefined` in the browser | Scoped `RUN_TIME` only | Must be `RUN_AND_BUILD_TIME`; Next inlines it at build. |
| Every plan shows the whole env set changing | DO returns `EV[1:...]` ciphertext for `SECRET` values | See `modules/wedding-app/README.md`, "SECRET env perpetual-diff caveat". |
| App cannot reach Postgres | Firewall has no rule for this app | Check `terraform output` on the data module: `firewall_managed` must be true and `allowed_app_ids` must contain the app id. |
| Backend write fails with an opaque `400` | Spaces rejecting AWS checksum headers | `skip_s3_checksum = true` must be in the backend block. |
| `terraform init` cannot list workspaces | Wrong endpoint, or `AWS_*` not set to the Spaces key | Check `endpoints.s3` matches the bucket's region, and that both `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are exported. |
| Custom domain stuck pending | CNAME not resolving yet, or pointed at `app_url` instead of `app_default_ingress` | Verify with `dig +short <domain>`; the answer must be the `*.ondigitalocean.app` hostname. |
| `App Platform autoscaling…` precondition error | Autoscaling set on a Basic (`apps-s-*`) size | Move to a Professional (`apps-d-*`) size or set `autoscaling = null`. |

## Version pinning

| Component | Constraint | Where |
| --- | --- | --- |
| Terraform | `>= 1.9` | every `versions.tf` / `terraform` block |
| Terraform in CI | `1.13.3`, exact | `TF_VERSION` in both workflows |
| `digitalocean/digitalocean` | `~> 2.43` | every `required_providers` |

`.terraform.lock.hcl` **is committed** for each env, on purpose: it is what
makes a CI plan use the same provider build as the plan you ran locally. Bump
provider versions in their own PR, never alongside a functional change — a
provider upgrade and a config change in one diff make a surprising plan
impossible to attribute.
