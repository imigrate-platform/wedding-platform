# `wedding-data`

The data tier for one wedding: a Managed Postgres cluster with its own database
and role, a Spaces bucket for guest photos and video, a CDN in front of that
bucket, and a trusted-sources firewall on the cluster.

Nothing in here is shared between weddings. Two weddings never touch the same
cluster, the same bucket or the same credentials.

---

## Usage

```hcl
module "data" {
  source = "../../modules/wedding-data"

  wedding_slug = "muskan-sourav"
  environment  = "production"

  region        = "blr1"
  spaces_region = "blr1"
  vpc_uuid      = data.terraform_remote_state.shared.outputs.vpc_uuid

  db_size       = "db-s-1vcpu-1gb"
  db_node_count = 1

  # Wire the app in so Postgres only accepts connections from it.
  allowed_app_ids      = [module.app.app_id]
  allowed_ip_addresses = ["203.0.113.10/32"] # office egress, for migrations

  cors_allowed_origins = ["https://muskan-sourav.imigrate.com"]
}
```

Then hand the outputs to `wedding-app`:

```hcl
module "app" {
  source = "../../modules/wedding-app"

  database_url   = module.data.database_uri
  spaces_bucket  = module.data.bucket_name
  spaces_region  = module.data.bucket_region
  spaces_cdn_url = module.data.cdn_url
  # ...
}
```

### There is no dependency cycle here

`module.data`'s **firewall** depends on `module.app`, while `module.app`
depends on `module.data`'s **cluster**. That looks circular at the module level
but is not: Terraform flattens modules and builds the graph per *resource*.
The real order is

```
database_cluster -> database_db / database_user -> app -> database_firewall
```

On the very first apply the app id is unknown at plan time, so the firewall
rule shows as `(known after apply)`. That is expected.

## Bucket ACL model

**The bucket is private. Individual objects are made public at upload time.**

The application uploads guest media with `x-amz-acl: public-read` on each
object. The Spaces CDN then serves those objects; the bucket itself stays
`private`.

Why not simply make the bucket public:

- A public bucket also exposes `ListObjects`. Anyone who learns the bucket
  hostname could enumerate every photo of every guest at the wedding. Per-object
  ACLs give the same CDN behaviour without the directory listing.
- It keeps the blast radius of a leaked read URL to one file.

The tradeoff, stated plainly: a public-read object is readable by anyone who has
its URL. Object keys are unguessable, but they are not a permission. If a
wedding needs media that is genuinely private, stop setting `public-read` on
upload and serve pre-signed GET URLs from the app instead — the bucket ACL does
not have to change, only the app's upload path and read path.

## Lifecycle rules

Two are always on:

| Rule | Why |
| --- | --- |
| `reap-incomplete-multipart-uploads` | Guests upload video over patchy venue wifi. Abandoned multipart uploads are invisible in the UI and are billed as storage. |
| `expire-noncurrent-versions` | Only when `bucket_versioning_enabled`. Keeps the safety net of versioning without paying for it forever. |

## Tagging & labelling

Only `digitalocean_database_cluster` accepts `tags` in this module — Spaces
buckets and CDN endpoints have no tag argument in the DigitalOcean API. So the
wedding slug and environment are carried three ways:

1. **DO tags** on the cluster: `imigrate`, `wedding:<slug>`, `env:<environment>`,
   `component:data`, plus anything in `extra_tags`.
2. **Resource names**: every resource is named `<slug>-<environment>-*` or
   `<slug>-media-<environment>`.
3. **DO project membership**: the calling stack files the cluster and bucket
   URNs into a per-wedding project, which is what the billing page groups by.

## Secrets and state

`digitalocean_database_user.app.password` is generated by DigitalOcean, not by
Terraform — no secret is ever chosen in the configuration. But the generated
value **is written to state**, as is the assembled `database_uri`. Marking the
outputs `sensitive = true` only masks console output; it does not encrypt state.

Consequences you must design around:

- The state bucket is as sensitive as the database password. Keep it private,
  keep versioning on it, and restrict its Spaces key.
- Anyone who can run `terraform output -raw database_uri` has production
  Postgres.
- To rotate, taint the user: `terraform taint 'module.data.digitalocean_database_user.app'`,
  then apply and redeploy the app so it picks up the new `DATABASE_URL`.

## Known provider limitations

- **No Spaces key resource.** DigitalOcean provider 2.43–2.48 cannot create or
  rotate Spaces access keys, so both Terraform's own Spaces credentials and the
  ones the app uses are supplied from outside Terraform. Create them in the DO
  control panel under **API → Spaces Keys**.
- **`cors_rule` on `digitalocean_spaces_bucket` is deprecated** and cannot set
  `expose_headers`, which browsers need to read `ETag` back from a multipart
  upload. This module uses the dedicated
  `digitalocean_spaces_bucket_cors_configuration` resource instead.
- **Storage can only grow.** `db_storage_size_mib` cannot be reduced; a
  reduction is rejected by the API, not by Terraform.
